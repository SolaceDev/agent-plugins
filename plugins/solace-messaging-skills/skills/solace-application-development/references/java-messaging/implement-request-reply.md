# Implement: Request-Reply (Direct) leaf

The per-leaf wiring for the Request-Reply (Direct) leaf of the Java API. Read this file from `implement-mode.md` Step 4 when the `Pattern` field is `Request-Reply (Direct)`. The shared Step 4 rules in `implement-mode.md` (the AI-assisted disclaimer header, the shared `SolaceConnectionConfig` helper, the variant discipline, the demo-harness rule, the comments rule, the explicit-single-class-imports rule, and the Quickstart fail-fast rule) apply here unchanged.

This is the ONLY Java API request-reply leaf in this skill: the reference samples cover request-reply over direct messaging only. There is no Request-Reply (Guaranteed) leaf and no guaranteed requestor or replier sample; a design that needs a persisted request is a Guaranteed Pub/Sub leaf with an application correlation id (`design-mode.md` Step 2), never this one.

## Request-reply flow

Generation reads ONE requestor sample and ONE replier sample and adapts each into its own generated class, the same near-verbatim discipline the other leaves use. Direct request-reply is at-most-once on both legs: there is no broker receipt and no redelivery, so this leaf has NO queue, NO provisioning, and NO client acknowledgement. The API manages the reply: the requestor's `RequestReplyMessagePublisher` sets the reply-to and a unique correlation id on each request and correlates the reply, and the replier's `Replier.reply()` routes to that reply-to and copies the correlation id. The requestor therefore needs no reply subscription and no correlation id of its own.

- `java-messaging-direct-requestor-blocking-sample.java` (the BASE requestor): basic-auth connect, a `RequestReplyMessagePublisher`, several blocking `publishAwaitResponse()` calls in sequence on the one connection, each with a POSITIVE `REQUEST_TIMEOUT_MS`, a `TimeoutException` catch, service event listeners registered before `connect()`, and a graceful SIGINT/SIGTERM shutdown. Only one request is outstanding at a time, each reply is processed before the next request goes out, and the requestor stops at the first request without a reply. It exits 0 when every request sent got its reply and 1 otherwise.
- `java-messaging-direct-requestor-sample.java` (the VARIANT requestor): the same, but several non-blocking `publish()` calls with one `ReplyMessageHandler`, so the requests are in flight together, and a wait for every result. It exits 0 only when every request sent got a reply.
- `java-messaging-direct-replier-sample.java` (the BASE replier): basic-auth connect, a `RequestReplyMessageReceiver` built with the request topic subscription (no queue, no provisioning), bounded request and reply buffers, a `receiveAsync()` `RequestMessageHandler` that guards on a `null` replier and answers with `replier.reply()`, a reply failure listener, service event listeners registered before `connect()`, and a graceful SIGINT/SIGTERM shutdown. It answers both requestor shapes.
- `java-messaging-direct-replier-blocking-sample.java` (ONLY when the Custom blocking-receive knob is ticked, `custom-mode.md`): the same receiver, buffers, and guard, but NO `receiveAsync()`: the main loop takes each request with `receiveMessage(handler, timeout)` and a POSITIVE timeout, and the handler runs on the application's own thread.

**Base requestor and variant.** Generate the blocking requestor when the design summary's `Consumption endpoint` reads `API-managed reply (RequestReplyMessagePublisher)` (the default): one request at a time, with the blocking call as the synchronization point, the same shape as the JCSMP and the Python direct requestors. When the summary records the VARIANT (for example `API-managed reply (RequestReplyMessagePublisher, non-blocking publish)`, chosen because many requests must be in flight at once), read the non-blocking sample instead. Read only the requestor sample the design chose and only the replier sample the run selects.

Each class builds its OWN `MessagingService`. Keep the samples' structure: `setupSolace(...)`, the main step, and `teardownSolace()` in `main`'s `finally`, with the shutdown hook that joins the main thread. Keep every listener and handler class.

**Ground before you write.** Before writing either class, WebFetch [Request-Reply Messaging in the Solace Java API](https://docs.solace.com/API/API-Developer-Guide-Java/Java-API-Request-Reply.md) in this session (SKILL.md Invariant 2).

## Replier class (near-verbatim `DirectReplier`, or `DirectReplierBlocking` on the blocking knob)

The Replier subscribes directly to the request topic (no queue), answers each request, and is the long-running process the developer runs FIRST. Start the file with the disclaimer header (the exact two lines `implement-mode.md` Step 4 defines), then wire it in this sequence:

1. Build the service `Properties` with `SolaceConnectionConfig.load(args, APP_NAME).toServiceProperties()`, then the service with `MessagingService.builder(ConfigurationProfile.V1).fromProperties(properties).build()` (on Quickstart without the two reconnect `putIfAbsent` lines, per the fail-fast rule). Register the three service event listeners BEFORE `connect()`, as the sample does.
2. `messagingService.connect()`. Immediately after `connect()` returns, emit the connect marker: `trace("VERIFY: CONNECTED");`.
3. Build the receiver as the sample does: `requestReply().createRequestReplyMessageReceiverBuilder()` with `fromProperties(receiverProperties)` (the two `ReceiverProperties.DIRECT_BACK_PRESSURE_*` properties that bound the request buffer) and `onReplierBackPressureReject(REPLY_BUFFER_CAPACITY)`, then `build(TopicSubscription.of(requestTopic))` for the design summary's topic. Keep `receiver.setReplyFailureListener(...)` BEFORE `receiver.start()`.
4. Base shape: `receiver.start()`, then `receiver.receiveAsync(handler)`, in the order the sample has them. Immediately after `receiveAsync(...)` returns, emit the subscribed marker: `trace("VERIFY: SUBSCRIBED");`. Blocking shape: NO `receiveAsync()`; `receiver.start()` alone, then the marker immediately after `start()` returns. **No reapply-subscriptions line.** The sample's comment states that `ConfigurationProfile.V1` already sets `ServiceProperties.RECEIVER_DIRECT_SUBSCRIPTION_REAPPLY` to `true`. Keep that comment and do not set the property.
5. In the handler's `onMessage(message, replier)`, keep the sample's discard check and its guard: a `null` replier means the message has no reply-to or no correlation id, so log it and return. After the guard, emit the request marker: `trace("VERIFY: REQUEST_RECEIVED");`. Then build the reply with the handler's one `OutboundMessageBuilder` and answer with `replier.reply(reply, replyProperties)`, inside the sample's two catch branches. Use `replier.reply()`, never a manual publish to the reply-to: the API routes and correlates the reply. On the blocking shape the same method body is the handler that `receiveMessage(handler, RECEIVE_TIMEOUT_MS)` runs on the main thread; keep the POSITIVE timeout and the loop's `RuntimeException` branch.
6. KEEP the long-running wait loop (on the blocking shape, the `receiveMessage()` loop itself), the shutdown hook, and `teardownSolace()` with `receiver.terminate(gracePeriod)` before `messagingService.disconnect()`. Keep each sample's own `TERMINATE_GRACE_PERIOD_MS` and `SHUTDOWN_WAIT_MS`: the samples' comments state that `terminate()` can take up to two grace periods. The Replier is the SIGINT target, and its shutdown line (`Shutdown signal received ...`) stays a `trace(...)` call.

## Requestor class (near-verbatim `DirectRequestorBlocking`, or `DirectRequestor` on the variant)

The Requestor connects, sends its requests, collects the replies, and exits on its own. It does NOT provision anything and does NOT wait for a key press or a signal. Start the file with the disclaimer header, then wire it in this sequence:

1. Build the service `Properties` and the service exactly as the Replier does (step 1 above), and register the three service event listeners BEFORE `connect()`.
2. `messagingService.connect()`. Immediately after `connect()` returns, emit the connect marker: `trace("VERIFY: CONNECTED");`.
3. Build the requestor as the sample does: `requestReply().createRequestReplyMessagePublisherBuilder().build()`, then `requestor.start()`.
4. Base shape: build each request with the one `OutboundMessageBuilder` and a `byte[]` payload, and send it to the design summary's topic with `requestor.publishAwaitResponse(request, requestTopic, REQUEST_TIMEOUT_MS)`. Keep the POSITIVE `REQUEST_TIMEOUT_MS`, the `TimeoutException` catch, and the `RuntimeException` catch. Keep the sample's loop: one requestor and one connection for every request, one request outstanding at a time, and a stop at the first request without a reply. Do NOT add a retry: the sample's comment marks the timeout as the place where an application adds its own retry policy. When the design chains requests, build the next request from the reply just received and send it to the next topic in the chain. Never generate a class that connects, sends one request, and exits as its fixed shape; a real application's own requests replace the sample's loop (the demo-harness rule). Variant: keep the sample's send phase (one `publish(request, replyHandler, msgId, requestTopic, REQUEST_TIMEOUT_MS)` per request), its `ReplyMessageHandler`, and its wait phase.
5. Emit the reply marker once for each reply, after the reply is processed: `trace("VERIFY: REPLY_RECEIVED");` (base shape: after the payload read in the loop; variant: in the handler's reply branch, before the counter). Keep the sample's exit code rule: 1 when a request sent got no reply, 0 otherwise (a shutdown signal before the reply is a clean stop).
6. Self-exit: return from the main step, and `teardownSolace()` in `main`'s `finally` calls `requestor.terminate(gracePeriod)` and then `messagingService.disconnect()`. Keep the shutdown hook, so Ctrl-C during the reply wait still reaches teardown.

## The marker contract and the named exec executions

These four `VERIFY:` marker strings (`VERIFY: CONNECTED`, `VERIFY: SUBSCRIBED`, `VERIFY: REQUEST_RECEIVED`, `VERIFY: REPLY_RECEIVED`) are the same strings the JCSMP and the Python Request-Reply (Direct) leaves emit, character for character. They are read PER PROCESS: the Replier output carries `SUBSCRIBED` and `REQUEST_RECEIVED`, the Requestor output carries `REPLY_RECEIVED`, and both print `CONNECTED`. The Java API has no verify script yet (`implement-mode.md` Step 5), but the markers are the contract that script will read, so never change one.

**Expose both mains through two named exec executions.** The generated pom declares two `exec-maven-plugin` `<execution>` blocks, one with `<id>requestor</id>` and one with `<id>replier</id>`, each with its own `<configuration><mainClass>`, in the same form as the snippet in `implement-guaranteed-pubsub.md`. The run commands in `implement-mode.md` Step 5 address them as `mvn exec:java@replier` and `mvn exec:java@requestor`.

**A passing run.** The Replier prints `VERIFY: CONNECTED` and then `VERIFY: SUBSCRIBED`; the Requestor prints `VERIFY: CONNECTED`, the Replier prints `VERIFY: REQUEST_RECEIVED` for each request, and the Requestor prints `VERIFY: REPLY_RECEIVED` for each reply and exits with status 0. A request sent before the Replier has subscribed gets no reply and times out, so the Replier always runs first.
