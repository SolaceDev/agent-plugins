# Implement: Direct Pub/Sub leaf

The per-leaf wiring for the Direct Pub/Sub leaf of the Java API. Read this file from `implement-mode.md` Step 4 when the `Pattern` field is `Direct Pub/Sub`. The shared Step 4 rules in `implement-mode.md` (the AI-assisted disclaimer header, the shared `SolaceConnectionConfig` helper, the variant discipline, the demo-harness rule, the comments rule, the explicit-single-class-imports rule, and the Quickstart fail-fast rule) apply here unchanged.

## Direct pub/sub flow

Generation reads the direct publisher sample and ONE direct subscriber sample, and adapts each into its own generated class, the same near-verbatim discipline the guaranteed flow uses. Direct messaging is at-most-once: there is no broker receipt and no redelivery, so this leaf has NO queue, NO provisioning, NO client acknowledgement, and NO publish receipt listener.

- `java-messaging-direct-publisher-sample.java`: basic-auth connect, a continuous DIRECT binary publish loop with a rotating payload to a dynamic topic, a publish failure listener for the asynchronous failures the API reports, capacity-bounded back pressure, service event listeners registered before `connect()`, and a graceful SIGINT/SIGTERM shutdown. No receipt listener and no user context (direct has no broker receipt). Generation STRIPS the continuous loop, the rotating payload, the dynamic topic, and the stats thread down to a short bounded burst that self-exits (Publisher steps below). The direct publisher has no blocking variant: `publish()` has no receipt to await.
- `java-messaging-direct-subscriber-sample.java` (the BASE shape): basic-auth connect, a plain topic subscription on a direct receiver (no queue, no provisioning), a `receiveAsync()` message handler, capacity-bounded back pressure with discard detection, service event listeners registered before `connect()`, and a graceful SIGINT/SIGTERM shutdown. The Subscriber is the long-running SIGINT target.
- `java-messaging-direct-subscriber-blocking-sample.java` (ONLY when the Custom blocking-receive knob is ticked, `custom-mode.md`): the same subscription, back pressure, and discard detection, but NO `receiveAsync()` handler: the main loop pulls each message with `receiveMessage(timeout)` and a POSITIVE timeout and processes it on the application's own thread.

Read ONLY the subscriber sample the run selects, never both. Each class builds its OWN `MessagingService` (two services, one per class, matching the samples). Keep the samples' structure: `setupSolace(...)`, the main loop, and `teardownSolace()` in `main`'s `finally`, with the shutdown hook that joins the main thread. Keep the three service event listeners and the publish failure listener; they are part of the best-practices contract and must not be stripped during adaptation.

**Ground before you write.** Before writing either class, WebFetch [Publishing Direct Messages](https://docs.solace.com/API/API-Developer-Guide-Java/Java-DM-Publish.md) and [Consuming Direct Messages](https://docs.solace.com/API/API-Developer-Guide-Java/Java-DM-Subscribe.md) in this session (SKILL.md Invariant 2).

## Subscriber class (near-verbatim `DirectSubscriber`, or `DirectSubscriberBlocking` on the blocking knob)

The Subscriber subscribes directly to the topic (no queue), receives on a handler (base shape) or pulls on its main loop (blocking shape), and is the long-running process the developer runs FIRST. Start the file with the disclaimer header (the exact two lines `implement-mode.md` Step 4 defines), then wire it in this sequence:

1. Build the service `Properties` with `SolaceConnectionConfig.load(args, APP_NAME).toServiceProperties()`, then the service with `MessagingService.builder(ConfigurationProfile.V1).fromProperties(properties).build()` (on Quickstart without the two reconnect `putIfAbsent` lines, per the fail-fast rule). Register the three service event listeners BEFORE `connect()`, as the sample does.
2. `messagingService.connect()`. Immediately after `connect()` returns, emit the connect marker: `trace("VERIFY: CONNECTED");`.
3. Build the direct receiver as the sample does: `createDirectMessageReceiverBuilder()` with `withSubscriptions(TopicSubscription.of(topic))` for the design summary's topic and `onBackPressureDropLatest(RECEIVE_BUFFER_CAPACITY)`, then `build()`. There is NO queue and NO missing-resources creation strategy on the direct path.
4. Base shape: `receiver.start()`, then `receiver.receiveAsync(handler)`, in the order the sample has them. Immediately after `receiveAsync(...)` returns, emit the subscribed marker: `trace("VERIFY: SUBSCRIBED");`. Blocking shape: NO `receiveAsync()`; `receiver.start()` alone, as the blocking sample does, then the marker immediately after `start()` returns. **No reapply-subscriptions line.** The JCSMP direct subscriber must set `REAPPLY_SUBSCRIPTIONS` to `true`, or its subscription is lost on an automatic reconnect. The Java API needs no such line: the sample's comment states that `ConfigurationProfile.V1` already sets `ServiceProperties.RECEIVER_DIRECT_SUBSCRIPTION_REAPPLY` to `true`. Keep that comment and do not set the property.
5. Base shape: in the handler's `onMessage`, keep the sample's payload read (`getPayloadAsBytes()`) and its discard check (`getMessageDiscardNotification()`). Blocking shape: in the main loop, keep the sample's `receiver.receiveMessage(RECEIVE_TIMEOUT_MS)` call with its POSITIVE timeout in milliseconds and its `RuntimeException` branch, and hand each returned message to the sample's processing method with the same payload read and discard check; `null` means a timeout, and the loop goes round to its shutdown check. On both shapes, after the discard check, emit the receipt marker: `trace("VERIFY: MESSAGE_RECEIVED");`. There is NO `ack()` on the direct path.
6. KEEP the long-running wait loop (on the blocking shape, the `receiveMessage()` loop itself), the shutdown hook, and `teardownSolace()` with `receiver.terminate(gracePeriod)` before `messagingService.disconnect()`. On the blocking shape keep the sample's `TERMINATE_GRACE_PERIOD_MS` of 0 and its `IncompleteMessageDeliveryException` warning: the loop has stopped, so nothing drains the buffer, and a dropped direct message is a normal at-most-once stop. The Subscriber is the SIGINT target, and its shutdown line (`Shutdown signal received ...`) stays a `trace(...)` call.

## Publisher class (near-verbatim `DirectPublisher`)

The Publisher only connects and publishes a short bounded burst of DIRECT messages, then exits on its own. It does NOT provision anything and does NOT wait for a key press or a signal. Start the file with the disclaimer header, then wire it in this sequence:

1. Build the service `Properties` and the service exactly as the Subscriber does (step 1 above), and register the three service event listeners BEFORE `connect()`.
2. `messagingService.connect()`. Immediately after `connect()` returns, emit the connect marker: `trace("VERIFY: CONNECTED");`.
3. Build the publisher as the sample does: `createDirectMessagePublisherBuilder().onBackPressureWait(PUBLISH_BUFFER_CAPACITY).build()`, then `publisher.setPublishFailureListener(...)` BEFORE `publisher.start()`, as the sample orders them. Direct has no broker receipt, so a buffered message that cannot be sent is reported only through that listener.
4. Publish a SHORT BOUNDED BURST to the design summary's topic in a small fixed-count loop: one reused `OutboundMessageBuilder`, `build(payload, messageProperties)` with a `byte[]` payload, and `publisher.publish(message, Topic.of(topic))` with no user context. Then return from the publish step. REMOVE the sample's continuous loop, its rotating payload and dynamic topic, and its stats thread, together with the thread's `shutdown()` call in `teardownSolace()` and its imports. Keep the sample's two catch branches around `publish()`. `teardownSolace()` in `main`'s `finally` calls `publisher.terminate(gracePeriod)`, which gives the buffered messages up to the grace period to leave before `disconnect()`. Keep the shutdown hook, so Ctrl-C during a back pressure wait still reaches teardown. When the request describes a real application, its own messages replace the burst (the demo-harness rule). That replacement changes the payload and the topic, never the shape: a request that describes a continuous or high-rate feed still gets a Publisher that sends a bounded batch of the application's real messages and exits on its own. The continuous trigger is the developer's integration step after verification.
5. The Publisher emits NO send-side marker. Direct has no broker receipt, so there is no `PUBLISH_ACKED` analog; a marker after `publish()` would only prove the local call returned. The proof of the round trip is `VERIFY: MESSAGE_RECEIVED` in the Subscriber output.

## The marker contract and the named exec executions

These three `VERIFY:` marker strings (`VERIFY: CONNECTED`, `VERIFY: SUBSCRIBED`, `VERIFY: MESSAGE_RECEIVED`) are the same strings the JCSMP and the Python Direct Pub/Sub leaves emit, character for character. They are read PER PROCESS: the Subscriber output carries `SUBSCRIBED` and `MESSAGE_RECEIVED`, and both classes print `CONNECTED`. The Java API has no verify script yet (`implement-mode.md` Step 5), but the markers are the contract that script will read, so never change one.

**Expose both mains through two named exec executions.** The generated pom declares two `exec-maven-plugin` `<execution>` blocks, one with `<id>publisher</id>` and one with `<id>subscriber</id>`, each with its own `<configuration><mainClass>`, in the same form as the snippet in `implement-guaranteed-pubsub.md`. The run commands in `implement-mode.md` Step 5 address them as `mvn exec:java@subscriber` and `mvn exec:java@publisher`.

**A passing run.** The Subscriber prints `VERIFY: CONNECTED` and then `VERIFY: SUBSCRIBED`; the Publisher prints `VERIFY: CONNECTED` and exits with status 0; the Subscriber then prints `VERIFY: MESSAGE_RECEIVED`. A direct message published before the Subscriber has subscribed is lost, so the Subscriber always runs first.
